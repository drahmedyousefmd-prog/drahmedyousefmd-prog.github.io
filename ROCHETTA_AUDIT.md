## 3. Audit results per your checklist

### 1. Project structure — ✅ sound, small, monorepo-free
15 components, 5 lib modules, 5 app route files, 10 data files. No dead feature branches. Minor: `tsconfig.tsbuildinfo` regenerates locally (ignored).

### 2. HTML files — N/A at authoring time
HTML is generated by Next export. `out/index.html` = 221 KB + a 192 KB RSC payload sibling; case pages ≈ 40–45 KB. See §10.

### 3. CSS files — one origin, but large
`src/app/globals.css` (≈1,300 lines) holds tokens + all components + print styles. Tailwind utilities are also used heavily in JSX, so style location is split between CSS classes and utility strings — inconsistent, risk of drift.

### 4. JavaScript files — build artifacts only in `out/`; 11 chunks ≈ 647 KB
React runtime + App Router client hydration + lucide tree-shaken symbols. The RSC serialized payload is delivered as `.txt` siblings (`__next.*.txt`, `index.txt`, `case/*/__next.*.txt`…) — **332 `.txt` files ≈ 3.2 MB** in `out/`. These get committed onto `gh-pages` and are pure bloat for a static host (harmless functionally).

### 5. Images / assets
**No real images** exist (no photos, no illustrations — deliberate: avoids medical-image rights). Only `favicon.ico` (26 KB) + 5 unused template SVGs that ship to production. There is **no social `og-image`**, no `apple-touch-icon`.

### 6. Fonts — self-hosted, correct, but heavy
Cairo (4 weights) + Tajawal (3) + Inter (4) = 16 `.woff2` ≈ 348 KB total downloaded across the site. Self-hosting via `next/font` is the right approach (no external font CDN, respects CSP, RTL renders correctly). Weight overlap between Cairo/Tajawal can be trimmed.

### 7. Navigation — functional, flat
- Home: sticky navbar (anchors `#top`, `#categories`, `#contact`) + category cards → chapter pages.
- Chapter page: breadcrumb `الرئيسية / <chapter>` + card grid → case pages.
- Case page: back-to-chapter chip/button, Rx-column sticky actions (PDF/الرئيسية), mobile bottom-sheet + FAB.
- **Issue:** all cross-page navigation uses the View Transition API fallback writing `window.location` — works but bypasses Next `<Link>` prefetch/soft nav (site is static; acceptable).
- **Issue (SEO):** no breadcrumb **structured data**; no consistent page titles hierarchy on non-home pages beyond `"X — Rochetta"`.

### 8. Search
- Home: **search card** (text + category dropdown) filters the **entire inlined dataset client-side**. Works instantly for 72 records, but the full `prescriptions.json` (≈190 KB) must be shipped to and parsed by every home visitor.
- Chapter pages: same pattern, scoped to the chapter.
- No debounce, no URL state (`?q=`), no server index, no `aria-live` result announcements, no keyboard listbox navigation. Fine at this scale; won't scale.

### 9. Prescription data structure
```jsonc
{
  "id": "rochetta-001",
  "title": "Major Depressive Disorder",
  "subtitle": "...",
  "content": "[DIAGNOSIS]\n- bullet...\n[RX-الروشتة — 1st line]\n- Drug (Generic) | جرعة | سعر ج.م",
  "category": "Psychiatry",              // matches a chapter name exactly
  "chapterAr": "أعصاب / الطب النفسي",      // DUPLICATED in lib/chapters.ts
  "alternatives": "Name | price\n...",    // legacy field — see below
  "perDrugAlternatives": "Drug: Alt | price, Alt2 | p2",
  "drugInstructions": "⚠️/✅/❌ lines",
  "drugInteractions": "markdown-ish blocks with ❌/⚠️"
}
```
- **Format is bespoke "markdown-ish"** parsed by hand in `lib/content.ts` (`parseContent`, `parseRxLines`, `parseSeverityBlocks`, `parsePerDrugAlternatives`, `parseBulletLines`). No schema/validation/versioning.
- Field `alternatives` appears **unused by the UI** (only `perDrugAlternatives` is consumed) → dead data.
- `chapterAr` duplicates `chapters.ts`; `category` duplicates chapter slugs — single source of truth missing. Content edits must happen in **two** places (master JSON + chapter JSON).

### 10. Responsive / mobile
- Desktop ≥1024px: split-screen case layout (1.3fr/1fr, sticky Rx column).
- <1024px: Rx column → **FAB + bottom sheet**; grids collapse 3→1 column.
- Mobile sheet lacks: drag-to-dismiss (only a visual handle), swipe backdrop, `Escape` close, **focus trap**, and `aria-modal`. Risky for keyboard users.
- `prefers-reduced-motion` is respected globally. No `h`-screen telescoping issues observed in code.

### 11. Accessibility — decent base, real gaps
✅ `lang=ar`, `dir=rtl`, aria-labels on primary controls, `aria-hidden` on decorative icons, focus states via brand border, print-friendly.
❌ **Tabs are not accessible tabs**: `role="tablist/tab/tabpanel"` exist but no `aria-controls`, no `id` linkage, no arrow-key navigation, no `aria-selected` toggling semantics mismatch (case-tab uses `aria-selected`, fine) — panels not wired.
❌ Bottom sheet: no focus trap / modal semantics.
❌ Color contrast: `--text-muted #8A938D` on white ≈ **3.2:1** — fails WCAG AA for body/small text; used on several captions/counts.
❌ No `aria-live` on search results count / empty state.
❌ Icon-only buttons in the Rx tabs rely on text (good), but the `cat-icon` visuals carry no `aria-label` (decorative — acceptable).
❌ Heading hierarchy largely fine (single `h1`), but home uses `h2` headings with identical visual weight classes — okay.

### 12. SEO — weakest area
- ✅ `lang`, `dir`, Arabic title, per-route `title`, semantic sections.
- ❌ **No Open Graph / Twitter cards**, no `og:image`, no `metadataBase` (Next warns).
- ❌ **No `robots.txt`, no `sitemap.xml`** in `public/` → static export ships neither (indexing depends on GitHub Pages' default crawler behavior).
- ❌ **No structured data (JSON-LD)** — a medical reference site should mark up `MedicalWebPage`, `MedicalCondition`/`Drug` entities, and breadcrumbs. Big opportunity.
- ❌ Chapter/case `generateMetadata` sets only `title`; no `description` (duplicates the root description), no canonical.
- ❌ No trailing canonicity strategy: both `/case/rochetta-001` and `/case/rochetta-001/` work → potential duplicate-content signals.
- ❌ `README.md` still contains the generic create-next-app text (including a claim about the **Geist** font) — inaccurate documentation.

### 13. Performance
- **Strengths:** fully static, no runtime API, fonts self-hosted, no third-party scripts, print CSS scoped, reduced-motion handled.
- **Biggest cost:** the **entire 72-prescription dataset is inlined** into the home page HTML/RSC payload ≈ **400 KB transferred** and re-hydrated per visit, purely to support client-side search.
- 647 KB JS across 11 chunks (React + framework + lucide). On a 3G mobile it's ~1.2–1.5 s of script parse.
- 332 `.txt` RSC siblings (+3.2 MB) bloat the `gh-pages` repo and the deploy.
- No image optimization concerns (no images). No lazy-loading, no code-splitting tuning (App Router static, acceptable).

### 14. Security — clean for a static site
- No auth, no forms (mailto only), no cookies, no CDN-external runtime scripts, no `dangerouslySetInnerHTML`, React output is escaped.
- **No secrets committed** (grep + `git ls-files` clean; no `.env*` exists; nothing in history).
- Missing: **Content-Security-Policy** meta — low risk on static host, but would harden against any injected inline script.
- Data is public medical reference content by design.
- Note: `mailto:` opens the user's mail client (no `target=_blank`) — works as intended (earlier bug fixed).

### 15. External dependencies

## 5. Recommended architecture

**Keep Next.js static export (no framework change needed).** It is the correct, best-fit architecture for a content-only medical reference on GitHub Pages.

Recommended target shape:

```
rochetta-web/
├── src/
│   ├── app/
│   │   ├── layout.tsx            # + metadataBase, OG/Twitter defaults, JSON-LD site block
│   │   ├── page.tsx              # home (server-rendered listing, no client dataset)
│   │   ├── not-found.tsx         # + sitemap/robots generation (app/sitemap.ts, robots.ts)
│   │   ├── chapter/[slug]/page.tsx
│   │   └── case/[id]/page.tsx
│   ├── components/               # unify CaseCard/CaseRowCard; extract handleNav; focus-trap sheet
│   ├── lib/
│   │   ├── content.ts            # parse/validate
│   │   ├── chapters.ts           # SINGLE source for chapterAr/icons/colors
│   │   └── search.ts             # optional: prebuilt client index (small JSON) winnowed from full data
│   └── data/
│       └── prescriptions.json    # THE ONLY data store (drop chapters/*.json duplicates)
├── public/                       # robots.txt, sitemap.xml, opengraph-image, remove unused SVGs
├── scripts/deploy.ps1            # export → prune .txt → push gh-pages (+ .nojekyll)
├── README.md                     # rewrite: purpose, stack, data schema, deploy runbook
```

Key decisions:
- **Single JSON data source.** Chapter pages already derive their lists via `getChapterByCategory` — make chapter pages filter the master file (same pattern case pages already use). Deletes 9 files.
- **Downshift home RSS/search payload:** server-render the home listings from the master data (as today) but hand the client only a **prebuilt search index** (id, title, subtitle, category, chapterAr) instead of full `content` strings (saves ~150 KB).
- **SEO layer:** `app/sitemap.ts` (`output:"export"` supports static sitemap), `app/robots.ts`, `opengraph-image` (SVG-based), per-route `description`, `canonical`, and a `jsonLd` helper for MedicalWebPage/BreadcrumbList per page.
- **Accessibility hardening:** proper tab widgets (ids, `aria-controls`, arrow keys), focus-trapped modal sheet with Escape, contrast bump for `--text-muted`, `aria-live` on search.
- **Deploy pipeline:** a committed `deploy` script that runs `next build`, prunes `out/**/*.txt` + template SVGs, ensures `.nojekyll`, and pushes `gh-pages`. (Still no CI; a GitHub Action is optional later.)
- **Content schema:** introduce a light `validate-master-data` script (ids unique, category ∈ chapters, prices parse) so edits are safe.

## 9. Risks

1. **De-duplication regression** — removing 9 JSON files must produce identical UI. Mitigating: Phase 0 tag + per-chapter count check + build-time validator.
2. **Payload pruning could break search** — if the slim index misses fields users search for (`content` currently searched). Mitigate: keep `content` in the index for now, or move search to a generated HTML page (`search?q=` unsupported on static export without JS; the JS client approach stays).
3. **SEO changes are not testable on a local `file://`** — require the live deploy to validate; GH Pages may take minutes to rebuild.
4. **Sitemap/robots on `gh-pages`** — must be regenerated on every deploy; sitemap URLs must reference the root domain (auto via `metadataBase`).
5. **User-site constraint** — this repo name owns the account root; any future second site at the same root is impossible (documented limitation, already accepted).
6. **No content backups** — until Phase 0, an accidental data edit is unrecoverable. Do Phase 0 first.
7. **Style-sheet split (CSS classes + Tailwind utilities)** — cosmetic churn if refactored aggressively; keep scope small.
